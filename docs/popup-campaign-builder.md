# Popup Studio: кампанії, правила та добірки

Вхід: **Інструменти → Попап-банери → Створити банер**, адреса `/tools/popup-banners/builder`.

## Перевірити альтернативи відсутнього товару

1. У «Сценарій і дані» застосувати сценарій **Альтернативи відсутнього товару**.
2. Вказати URL відсутнього товару підключеного магазину для прикладу. Це лише контекст прев’ю, а не правило прив’язки банера до однієї сторінки.
3. Налаштувати джерело добірки: категорія товару, категорія на рівень вище, конкретна категорія або ручний список. Включення дочірніх категорій задається окремо.
4. Натиснути «Редагувати шаблон картки». Зміна будь-якого вкладеного тексту, фото, кнопки або контейнера застосовується до всіх карток. Доступні окремі стилі Desktop і Mobile, сітка та горизонтальна карусель.
5. У «Правила показу» налаштувати додаткові групи І/АБО, виключення, момент, частоту, розклад і пріоритет.
6. У «Перевірка» перевірити URL, за потреби артикул модифікації та симульований стан наявності. Переглянути результат кожної умови, склад добірки, відхилені кандидати й конкуруючі кампанії.
7. Зберегти чернетку або опублікувати. Збереження змін активної кампанії не змінює її опубліковану версію до повторної публікації.

## Правила та дані

- Базова аудиторія поєднується з додатковими правилами через І. Збіг із виключеннями забороняє показ. Невідомі факти не задовольняють ані позитивні, ані негативні умови про товар.
- Підтримуються тип сторінки, наявність, товар, артикул модифікації, категорія з нащадками, бренд, наліпка, стан товару, повний URL і шлях. Умови мають типізовані оператори; групи обмежені 5 рівнями та 100 вузлами на дерево.
- «Товар відкритої сторінки», «Закріплений товар банера» та «Товар поточної картки добірки» — окремі джерела. Успадкування всередині добірки використовує поточну картку.
- Старий добір альтернатив використовував точну категорію товару, без обходу її предків. Новий вибір «Категорія на один рівень вище» робить цей перехід явним.
- Автоматична добірка використовує активні видимі доступні пропозиції поточного покоління каталогу. За замовчуванням виключає поточну модель разом із модифікаціями та обирає одну доступну пропозицію на іншу модель. Невідома наявність кандидата не вважається доступністю.
- Добірка має ліміт до 12 товарів, мінімум для показу, фільтри брендів, стану й цін та виключення товарів, брендів і категорій. Якщо товарів менше мінімуму у видимій добірці, банер приховується. Автоматичного переходу до сторонньої категорії немає.
- Карусель прокручується горизонтально нативним жестом/скролом. Шаблон картки — один контейнер; вкладені добірки, форми, таймери та підтвердження всередині нього не допускаються.
- Вибір нового сценарію або шаблона показує підтвердження заміни макета та правил. Частота, розклад і промокод зберігаються. Історія дизайну скасовує зміни макета, а не налаштування кампанії.
- Дати, дні тижня та інтервал годин редагуються в часовому поясі кампанії. Симуляція дати у перевірці явно використовує часовий пояс пристрою.
- Мінімальна затримка застосовується до всіх тригерів. На сайті спочатку враховуються пристрій і частота, потім готовність події. Серед готових кампаній перемагає вищий пріоритет; за однакового пріоритету використовується порядок оновлення кампаній. За один цикл оцінки показується одна кампанія.

## Відповідність сценаріїв

| Сценарій | Новий конструктор | Перевірка |
| --- | --- | --- |
| Альтернативи відсутнього товару | Динамічна добірка + правила наявності | API, вкладені правила, мінімум, категорії та ручний список; реальний storefront Desktop/Mobile |
| Товарна пропозиція | Товар банера або окремий товарний блок | Збереження, повторне відкриття, прив’язки та кошик Desktop/Mobile |
| Інформація / підтвердження | Довільний макет + блок «Підтвердження» + дія кнопки | Checkbox блокує дію; подія acknowledge; Desktop/Mobile |
| Промокод | Блок промокоду, власний код або бібліотека | Попередні API та runtime тести збережені |
| Контактна форма за промокод | Форма, довільні поля, результат із промокодом | Реальне збереження контакту та прихований до відправлення код Desktop/Mobile |
| Таймер | Блок таймера, дата або тривалість | Обидва режими API; приховування у storefront |
| Власний банер | Порожній макет, вкладені контейнери та всі блоки | Історія, drag/drop, JSON, адаптивні стилі |

## Контракти реалізації

Нова схема не потребує міграції БД: правила зберігаються у наявному JSONB `targeting`, конфігурація добірки — у `block_document`. Опублікований snapshot містить їх разом із макетом.

`POST /api/popup-banners/inspect` — авторизована перевірка чернетки. Вона не завантажує довільний URL мережею, а зіставляє його з каталогом підключеного магазину. Стан DOM, історія відвідувача та настання події не доступні серверу: джерело наявності й симуляція частоти підписані явно. Конкуренти показані як можливі, без вигаданого висновку про історію конкретного відвідувача.

`GET /api/public/popup-banners/resolve?allCandidates=true` додає список придатних кампаній для клієнтського вибору за частотою та готовністю події; запит без параметра зберігає попередній контракт першої кампанії. Форма за промокод не розкриває свій код у жодному публічному кандидатові.

Storefront-селектори Desktop/Mobile не замінювалися. E2E використовує окремі DOM-фікстури й одночасно мобільний User-Agent та viewport. Редактор і перевірка не змінюють каталог; контакти та кошик створюються лише під час справжньої взаємодії на сайті.
