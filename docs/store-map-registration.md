# Реєстрація магазинів продавцями

Реалізовано міграціями `100_store_map_registration.sql` і `101_store_map_reusable_registration.sql`.
Дані належать модулю `store-map`.

## Сценарій

У **Мапа магазинів → Заявки** постійно показане одне багаторазове посилання
`https://<домен-кабінету>/store-map/register`. Його можна копіювати в будь-який момент
і надсилати всім продавцям. Створення окремого посилання, token і строку дії немає.

Продавець відкриває HTTPS-посилання на телефоні без облікового запису, заповнює назву, місто,
адресу, щоденний графік `09:00 - 20:00` і необов’язковий коментар. Поля коду магазину немає.
Заявка не додає торгову точку автоматично. Після відправлення форма показує підтвердження
отримання та кнопку **Зареєструвати ще один магазин**. Кожна нова форма очищає попередні дані
й геолокацію та отримує власний UUID `submissionId`. Повторне відкриття того самого посилання
показує порожню форму; інші продавці можуть користуватися ним одночасно.

Раніше видані одноразові посилання з token після `#` зберігають попередню поведінку, строки дії
та прив’язку до історичних заявок. У новому інтерфейсі генератора таких посилань немає.

У кабінеті доступні пошук, фільтр за статусом, пагінація по 30 записів і лічильник нових заявок.
Відповідальний відкриває заявку, перевіряє заповнення й карту, за потреби змінює дані та маркер,
схвалює або відхиляє заявку. Схвалення створює активний магазин; код залишається порожнім.
Звичайне редагування торгової точки й імпорт/експорт продовжують підтримувати код.

## Геолокація та її обмеження

Позиція запитується лише після натискання кнопки та з браузерним дозволом:
`watchPosition`, `enableHighAccuracy: true`, `maximumAge: 0`, timeout одного очікування 20 с.
Вікно збору триває до 60 с; після 15 с продавець може завершити його раніше за наявності заміру.
Стеження й таймери припиняються після завершення, відмови в дозволі або закриття форми.

Приймаються свіжі скінченні координати з додатною оцінкою точності. Дублікати й застарілі
callbacks відсіюються. Із останніх 120 вимірювань обирається найменший заявлений радіус серед
вимірювань, узгоджених хоча б з одним іншим: відстань між ними не більша за суму похибок
(мінімальний допуск 10 м). Якщо узгодженої пари немає, найкращий наявний замір показується з
попередженням. Це перевірка узгодженості, а не нова оцінка фізичної точності. Усереднення не
створює штучно зменшеної похибки.

Похибка понад 50 м позначається для особливої перевірки, але не блокує подання. У формі
потрібно підтвердити перевірку маркера. Відмова в геолокації не підміняється геокодуванням адреси
або серверною IP-локацією: продавець бачить інструкцію й може повторити спробу.

API браузера сам обирає GPS, Wi-Fi та інші джерела; сторінка не сканує Wi-Fi і не може
примусово обрати провайдера. Висока точність є побажанням, а не гарантією. Дані клієнта,
включно з `accuracy` і timestamp, не є доказом фізичної присутності.

У заявці окремо зберігаються:

- початкові поля й обраний продавцем маркер (`submittedData`), незмінні при розгляді;
- початковий замір (`measurement`): координати, радіус похибки, час, кількість вимірювань,
  тривалість вікна й ознака узгодженості;
- кінцеві поля й маркер, затверджені відповідальним;
- статус, версія, коментар, автор і час рішення, ID створеного магазину.

Фіолетовий маркер нерухомий у центрі карти: продавець або відповідальний пересуває саму карту
пальцем, мишею чи клавіатурою. Після завершення руху, включно з інерцією, беруться координати
центра. Натискання на інше місце карти не переставляє маркер. Підтвердження й надсилання/схвалення
заблоковані під час руху; попереднє підтвердження продавця скидається. Числове редагування та
**Повернути карту до заміру** синхронізують центр без повторних ручних змін. У режимі перегляду
та під час вимірювання/надсилання пересування вимкнено, масштаб можна змінювати кнопками.

Синє коло на карті завжди належить початковому заміру; вибір іншого центра не змінює його
координати чи похибку. Сервер відхиляє замір старший за 15 хвилин або більш ніж на 2 хвилини в майбутньому.
Для перевірки точної позиції входу потрібне тестування на фізичному телефоні безпосередньо біля
магазину; browser E2E перевіряють логіку на емульованій геолокації.

## Контракти

Усі захищені операції вимагають `requireAuth` і доступу `store_map`, включно з вимогою 2FA,
якщо вона налаштована для інструмента:

| Метод і шлях | Призначення |
| --- | --- |
| `POST /api/store-map/registration/links` | Створення: `{ label?: string }`; повертає metadata і одноразово `token` |
| `GET /api/store-map/registration/links` | Metadata останніх 100 посилань без token/hash |
| `POST /api/store-map/registration/links/:id/revoke` | Відкликання невикористаного посилання |
| `GET /api/store-map/registration/requests` | `{items,total,pendingCount,page,pageSize}`; query `status`, `search`, `page` |
| `GET /api/store-map/registration/requests/:id` | Повна заявка |
| `POST /api/store-map/registration/requests/:id/approve` | `{version,name,city,address,hoursText,latitude,longitude,reviewNote?}` |
| `POST /api/store-map/registration/requests/:id/reject` | `{version,reviewNote?}` |

Публічний `GET /api/public/store-map/registration` без Authorization повертає
`{status: 'OPEN', expiresAt: null, reusable: true}` і не розкриває раніше поданих даних.
POST без Authorization приймає обов’язковий UUID `submissionId`, основні поля,
маркер, `comment`, `confirmed: true`, `measurement` і повертає `{status: 'SUBMITTED'}`.
Нові подання не потребують рядка в `store_map_registration_links`; їх `linkId` дорівнює `null`.
Точні типи — `client/src/types/store-map.ts`; серверні межі й strict validation —
`src/modules/store-map/registration.routes.js`.

Для сумісності старі `links` API з таблиці вище та Bearer-token сценарій лишаються доступними.
Старий token — 32 криптографічно випадкових байти в base64url; у PostgreSQL зберігається SHA-256.
GET з token повертає `{status: 'OPEN'|'SUBMITTED', expiresAt}`. Відкликаний/прострочений token
повертає `410`, невідомий — `404`. Це не обмежує постійне публічне посилання.

Відповіді форм, заявок і посилань використовують `no-store`; публічні API не вмикають
cross-origin CORS і мають IP rate limit. Форма не передає cookies робочого простору.

Унікальний `submissionId` і SHA-256 від нормалізованих даних захищають нові подання від
мережевих повторів: однаковий ключ/payload, включно з одночасними POST, створює одну заявку.
Той самий ключ з іншими даними повертає `409`; нова форма має новий ключ. Для старого
одноразового посилання збережено row lock і одну заявку на `link_id`; частковий unique index
не застосовується до нових рядків із `link_id = NULL`.

Рішення використовує row lock і version check; зміна
застарілої або вже розглянутої заявки повертає `409`. Повтор однакового кінцевого рішення
ідемпотентний лише для того самого автора, версії та payload; конкурентні відмінні правки
повертають `409`. Створення магазину й схвалення виконуються в одній PostgreSQL-транзакції.

Карта розгляду ізольована в same-origin iframe `/store-map/location-preview` із тим самим
доступом `store_map`. Дані передаються лише через перевірені origin/source `postMessage`,
без координат у URL. CSP дозволяє OpenFreeMap лише для сторінки карти та MapLibre worker.

## Перевірки

`tests/store-map-registration.integration.test.js` перевіряє багаторазові й одночасні подання,
retry, доступ, сумісність зі старими expiry/revoke, validation, захист початкових даних,
version conflict, схвалення/відхилення й публічний feed.
`client/src/lib/store-map-location.test.ts` перевіряє заміри, відкидання кешу/ізольованих викидів,
таймери, відмову в дозволі й cleanup. `tests/e2e/store-map-registration.spec.ts` перевіряє
окремі desktop/mobile браузери, постійність URL, повторні подання з одного пристрою з новим
заміром, touch/mouse пересування під нерухомим маркером, блокування дій під час руху,
повернення до заміру та схвалення через справжню карту. `StoreMapCoordinatePicker.test.tsx`
перевіряє координати центра, відсутність feedback loop при синхронізації й read-only режим.
