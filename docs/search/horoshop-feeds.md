# Товарні фіди Хорошопа

Інструмент `/tools/horoshop-feeds` у категорії «Керування Хорошопом через API» доступний за правом `horoshop_feeds`. Адміністратор має доступ автоматично; іншим користувачам він надається через стандартне керування інструментами. Підтримується спільна вимога 2FA.

## Робочий сценарій

1. Використати чинне підключення Хорошопа та синхронізований каталог `search_horoshop_*`.
2. Знайти товари за назвою/артикулом, категорією, брендом, наявністю або вставити список назв чи артикулів по одному на рядок. Google Merchant Center і Facebook мають незалежні фільтри: усі статуси, увімкнено, вимкнено, частина модифікацій, немає даних. Обидва фільтри поєднуються між собою та з рештою умов. Статус відповідає колонці таблиці: «Частина модифікацій» — опція відрізняється між активними модифікаціями; «Немає даних» — хоча б одна модифікація має невідоме значення. Фільтрація виконується до пагінації та обмеження масової вибірки, використовує локальні дані каталогу й успадкування від батьківського товару. Артикул модифікації вибирає її батьківський товар; неоднозначні назви потребують вибору користувача. Локальний каталог смартфонів не використовується.
3. Вибрати окремі товари, усі рядки поточної сторінки прапорцем у заголовку таблиці або всі за фільтром (до 5000 батьківських товарів). Вибір усіх отримує точний список ID; після цього можна зняти будь-який рядок, зберігаючи решту вибору та вибір на інших сторінках. У режимі вставленого списку всі за фільтром означає лише товари цього списку. Доступні 10/25/50/100 рядків на сторінці, пошук у категоріях і кілька брендів.
4. У панелі вибірки під фільтрами натиснути «Масова дія». У бічній панелі праворуч для Google Merchant Center та Facebook незалежно вибрати «Не змінювати», «Додати до фіда» або «Прибрати з фіда». Кнопки підтвердження та скасування залишаються внизу панелі; скасування зберігає вибір товарів.
5. Натиснути «Перевірити зміни» у бічній панелі. Як у «Популярності товарів», відкривається окремий екран підготовки, а потім таблиця «було / буде» для Google та Facebook, деталі модифікацій і кнопка підтвердження. Preview створюється лише із синхронізованого PostgreSQL-каталогу і не чекає зовнішнього API. Помилка підготовки залишається на екрані з кнопками повтору й повернення.
6. Натиснути «Застосувати зміни». Відкривається екран прогресу. Worker читає актуальні фіди через API, виконує операцію, перевіряє результат повторним експортом і показує окремий екран результату. Історія відразу включає підтверджену операцію, оновлюється під час роботи та дозволяє знову відкрити деталі. Непідтверджені перегляди, як у «Популярності товарів», до історії виконання не входять.

## Контракт Хорошопа

Згідно з [українською документацією імпорту](https://horoshop.notion.site/1b6cc2897079812b9127de30b8fd106c), `catalog/import` приймає `article` та `export_to_marketplace` — повний список назв майданчиків через `;`. Використовуються стандартні назви `Google Feed for Merchant Center` і `Facebook Feed`, підтверджені [довідкою фідів](https://help.horoshop.ua/uk/articles/2446965) та [довідкою Facebook](https://help.horoshop.ua/uk/articles/2446975).

Інші майданчики зберігаються окремо для кожної модифікації. Не надсилаються ціни, описи, залишки, видимість чи інші властивості. Для виключення з останнього фіда передається явний порожній рядок; успіх визнається лише після read-back. Імпорт не повторюється автоматично при timeout, оскільки запис міг уже відбутися.

Експорт може бути плоским або містити `modifications`/`variants`. Worker явно запитує `includedParams: ["export_to_marketplace"]`, зберігаючи стандартні `article`/`parent_article` поля. Read-only перевірка підключеного магазину 11.11.2026 підтвердила формат `export_to_marketplace: [{ "id": 4, "value": "Facebook Feed" }]` у звичайному й обмеженому експорті. Назва береться з `value`; також підтримуються рядки, масиви рядків і об'єкти з `title`/`name`. ID не використовується для визначення фіда. Якщо поле модифікації відсутнє, допускається явне успадковане значення батьківського товару. Явний порожній список означає вимкнення; відсутнє, `null`, невідоме або некоректне значення означає невідомий стан.

Невідомий стан у локальному каталозі не заважає переглянути заплановані незалежні дії каналів. Він показується як «Немає даних», а не як вимкнений фід. Після підтвердження worker повинен прочитати повний поточний список майданчиків. Без цих даних він не виконує жодного імпорту; причина відмови залишається на екрані результату й в історії. Для відомих поточних значень зберігається перевірка конфлікту з переглянутим snapshot.

Інструмент змінює опцію товару, але не налаштування категорій, генерацію XML або статус схвалення в рекламній системі. Товар потрапить до актуального XML після генерації фіда в Хорошопі, якщо виконано інші вимоги майданчика. Див. [генерацію Facebook-фіда](https://help.horoshop.ua/uk/articles/2446975).

## Виконання та відновлення

- PostgreSQL зберігає чернетки, queue, immutable snapshots, статуси, автора й час операцій. Міграція `106` додає таблиці та право доступу; `107` — окремі `resolved_before`/`resolved_target` snapshots для доповнення невідомих даних перед записом без зміни оригінального перегляду.
- Перед першим записом повторно читаються всі вибрані товари. Зміна будь-якого списку фідів або складу модифікацій зупиняє нові записи операції як конфлікт. Прев'ю чинне одну годину; його можна застосувати лише один раз.
- Робота серіалізується з іншими записами Хорошопа через `runExclusiveExternalWrite` і advisory lock `72914213`. Прив'язка до connection/generation запобігає застосуванню операції до нового магазину.
- Після перезапуску queued/running операції відновлюються. Уже записаний результат спочатку перевіряється. Частково записана група модифікацій не переписується автоматично.
- Повний remote snapshot для початково невідомих фідів записується до БД перед імпортом. Відновлення використовує саме його; у деталях залишаються і початковий перегляд, і фактично перевірені значення. Історію та деталі можна читати під час синхронізації каталогу.
- Локальна проєкція оновлюється тільки для повністю підтвердженого результату. Решта записів доступна в історії як failed/conflict/partial. Новий перегляд завжди читає актуальні remote значення.
- Хорошоп не надає compare-and-swap для цього поля: незалежне редагування в адмінці між останньою перевіркою та імпортом не можна атомарно заборонити. Read-back виявляє непідтверджений результат; автоматичного rollback немає.

## API

Усі маршрути `/api/search/horoshop/feeds` вимагають авторизацію та `horoshop_feeds`, повертають стандартний `{ data }` / `{ error }` і `Cache-Control: no-store`.

| Метод | Маршрут | Призначення |
| --- | --- | --- |
| GET | `/catalog` | Сторінка каталогу, кешовані Google/Facebook стани, значення фільтрів |
| POST | `/catalog/selection` | Каталог у межах списку ID та фільтрів |
| POST | `/resolve` | Зіставити назви/артикули з товарами |
| POST | `/select` | Отримати точні ID всіх товарів за фільтром, опційно в межах `productIds` вставленого списку |
| POST | `/sync` | Запустити наявну синхронізацію каталогу |
| POST | `/operations/preview` | Створити snapshot без запису в магазин |
| POST | `/operations/:id/apply` | Поставити переглянуту операцію в чергу |
| GET | `/operations/:id` | Прогрес, snapshots і підтверджені результати |
| GET | `/operations` | Останні 50 запущених операцій поточного підключення |

```json
{
  "selection": { "filters": { "brands": ["Apple"] } },
  "action": { "google": "enable", "facebook": "disable" }
}
```

Замість `filters` можна передати `productIds: ["UUID"]`. Обидва канали `keep` відхиляються. Фільтри: `search`, `category`, `brands`, `availability`, `google`, `facebook`. Для двох статусів дозволено `""` (усі), `enabled`, `disabled`, `mixed`, `unknown`; пропущений параметр означає всі статуси. Вони підтримуються в GET `/catalog` і в `filters` маршрутів `/catalog/selection`, `/select`, `/operations/preview`. API приймає тільки дозволені канали й дії; довільні назви майданчиків з браузера не приймаються.

## Перевірки

Інтеграційні тести використовують ізольовану pg-mem базу та fake Horoshop API. Вони перевіряють збереження сторонніх фідів, незалежні опції каналів, порожній список, невідомі дані, зміну модифікацій, конфлікти, втрату відповіді, відновлення, read-back, права й 2FA. Окрема регресія покриває підтверджений у магазині формат `{ id, value }` у кеші, перегляді, записі, повторному читанні й історії. Desktop/mobile E2E використовують справжні Express-маршрути preview/apply/select/history, міграції та worker. Відповіді застосунку не перехоплюються; підмінено лише зовнішній транспорт `HoroshopClient`, включно з JSON-конвертом Хорошопа та реальним форматом масиву `{ id, value }`. Перевіряються вибір сторінки/всього каталогу, екран майбутніх змін до імпорту, підтвердження, фактичний результат, історія та видима відмова при недоступності даних. Fixture-контроль існує виключно в pg-mem E2E harness і не підключається до production app. Реальних товарів тести не змінюють.
