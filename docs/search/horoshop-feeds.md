# Товарні фіди Хорошопа

Інструмент `/tools/horoshop-feeds` у категорії «Керування Хорошопом через API» доступний за правом `horoshop_feeds`. Адміністратор має доступ автоматично; іншим користувачам він надається через стандартне керування інструментами. Підтримується спільна вимога 2FA.

## Робочий сценарій

1. Використати чинне підключення Хорошопа та синхронізований каталог `search_horoshop_*`.
2. Знайти товари за назвою/артикулом, категорією, брендом, наявністю або вставити список назв чи артикулів по одному на рядок. Артикул модифікації вибирає її батьківський товар; неоднозначні назви потребують вибору користувача. Локальний каталог смартфонів не використовується.
3. Вибрати окремі товари або всі за фільтром (до 5000 батьківських товарів). У режимі вставленого списку всі за фільтром означає лише товари цього списку.
4. Для Google Merchant Center та Facebook незалежно вибрати «Не змінювати», «Додати до фіда» або «Прибрати з фіда».
5. Натиснути «Перевірити зміни». Сервер перечитує поточний каталог через API і зберігає незмінний snapshot вихідного та цільового списку фідів кожної модифікації. Цей крок не змінює магазин.
6. Переглянути зміни та натиснути «Застосувати зміни». Worker виконує операцію, перевіряє результат повторним експортом і записує історію з автором, часом та результатом для кожного товару.

## Контракт Хорошопа

Згідно з [українською документацією імпорту](https://horoshop.notion.site/1b6cc2897079812b9127de30b8fd106c), `catalog/import` приймає `article` та `export_to_marketplace` — повний список назв майданчиків через `;`. Використовуються стандартні назви `Google Feed for Merchant Center` і `Facebook Feed`, підтверджені [довідкою фідів](https://help.horoshop.ua/uk/articles/2446965) та [довідкою Facebook](https://help.horoshop.ua/uk/articles/2446975).

Інші майданчики зберігаються окремо для кожної модифікації. Не надсилаються ціни, описи, залишки, видимість чи інші властивості. Для виключення з останнього фіда передається явний порожній рядок; успіх визнається лише після read-back. Імпорт не повторюється автоматично при timeout, оскільки запис міг уже відбутися.

Експорт може бути плоским або містити `modifications`/`variants`. Якщо поле модифікації відсутнє, допускається явне успадковане значення батьківського товару. Явний порожній список означає вимкнення; відсутнє, `null`, невідоме або некоректне значення означає невідомий стан. Якщо API не повертає придатний для перевірки `export_to_marketplace`, запис блокується, а не вгадується. Публічна документація експорту не гарантує форму цього поля для кожної версії Хорошопа.

Інструмент змінює опцію товару, але не налаштування категорій, генерацію XML або статус схвалення в рекламній системі. Товар потрапить до актуального XML після генерації фіда в Хорошопі, якщо виконано інші вимоги майданчика. Див. [генерацію Facebook-фіда](https://help.horoshop.ua/uk/articles/2446975).

## Виконання та відновлення

- PostgreSQL зберігає чернетки, queue, immutable snapshots, статуси, автора й час операцій. Міграція `106` додає нові таблиці та право доступу.
- Перед першим записом повторно читаються всі вибрані товари. Зміна будь-якого списку фідів або складу модифікацій зупиняє нові записи операції як конфлікт. Прев'ю чинне одну годину; його можна застосувати лише один раз.
- Робота серіалізується з іншими записами Хорошопа через `runExclusiveExternalWrite` і advisory lock `72914213`. Прив'язка до connection/generation запобігає застосуванню операції до нового магазину.
- Після перезапуску queued/running операції відновлюються. Уже записаний результат спочатку перевіряється. Частково записана група модифікацій не переписується автоматично.
- Локальна проєкція оновлюється тільки для повністю підтвердженого результату. Решта записів доступна в історії як failed/conflict/partial. Новий перегляд завжди читає актуальні remote значення.
- Хорошоп не надає compare-and-swap для цього поля: незалежне редагування в адмінці між останньою перевіркою та імпортом не можна атомарно заборонити. Read-back виявляє непідтверджений результат; автоматичного rollback немає.

## API

Усі маршрути `/api/search/horoshop/feeds` вимагають авторизацію та `horoshop_feeds`, повертають стандартний `{ data }` / `{ error }` і `Cache-Control: no-store`.

| Метод | Маршрут | Призначення |
| --- | --- | --- |
| GET | `/catalog` | Сторінка каталогу, кешовані Google/Facebook стани, значення фільтрів |
| POST | `/catalog/selection` | Каталог у межах списку ID та фільтрів |
| POST | `/resolve` | Зіставити назви/артикули з товарами |
| POST | `/sync` | Запустити наявну синхронізацію каталогу |
| POST | `/operations/preview` | Створити snapshot без запису в магазин |
| POST | `/operations/:id/apply` | Поставити переглянуту операцію в чергу |
| GET | `/operations/:id` | Прогрес, snapshots і підтверджені результати |
| GET | `/operations` | Останні 50 запущених операцій поточного підключення |

```json
{
  "selection": { "filters": { "brands": ["Apple"] } },
  "action": { "google": "enable", "facebook": "disable" }
}
```

Замість `filters` можна передати `productIds: ["UUID"]`. Обидва канали `keep` відхиляються. Фільтри: `search`, `category`, `brands`, `availability`. API приймає тільки дозволені канали й дії; довільні назви майданчиків з браузера не приймаються.

## Перевірки

Інтеграційні тести використовують ізольовану pg-mem базу та fake Horoshop API. Вони перевіряють збереження сторонніх фідів, незалежні опції каналів, порожній список, невідомі дані, зміну модифікацій, конфлікти, втрату відповіді, відновлення, read-back, права й 2FA. UI та desktop/mobile browser тести перевіряють окремі етапи preview/apply та межі вибірки. Реальних товарів автоматичні тести не змінюють.
