# Промокоди Хорошоп у KramKit

## Призначення та джерело істини

Розділ **«Промокоди»** є локальною бібліотекою маркетингових кодів для повторного використання в кампаніях KramKit. Сам код створюється і керується в Хорошопі. KramKit не створює промокоди в Хорошопі, не змінює їх і не застосовує код автоматично через DOM кошика або оформлення замовлення.

Запис у KramKit є довідковим каталогом для конкретного підключеного магазину. Однаковий код не можна додати двічі в межах одного магазину; порівняння виконується без урахування регістру. В іншого магазину може існувати код з таким самим значенням.

## Дані бібліотеки

Кожен запис містить:

- внутрішню назву;
- код;
- тип: відсотковий купон або сертифікат на фіксовану суму;
- розмір знижки;
- валюту для сертифіката;
- необов'язкові дату початку й завершення;
- необов'язковий ліміт використань як довідкове поле;
- примітку про бренди, категорії або інші обмеження;
- ознаку, що код перевірено в Хорошопі;
- ознаку ввімкнення запису в локальній бібліотеці.

Статус обчислюється з ознаки ввімкнення й дат:

- `active` — запис увімкнений, а поточний час входить у період дії;
- `scheduled` — дата початку ще не настала;
- `ended` — дата завершення минула;
- `disabled` — запис вимкнений у KramKit.

Вимкнення або видалення локального запису не змінює відповідний промокод у Хорошопі. Запис, який використовується кампаніями, не видаляється: його можна вимкнути.

## API бібліотеки

Усі endpoint-и вимагають автентифікації та доступу до інструмента попап-банерів:

- `GET /api/promo-codes` — список поточного магазину; підтримує `search` і `status`;
- `GET /api/promo-codes/:id` — один запис;
- `POST /api/promo-codes` — створення;
- `PUT /api/promo-codes/:id` — повне оновлення;
- `DELETE /api/promo-codes/:id` — видалення запису, який не використовується кампаніями.

Відповідь списку також містить кампанії, у яких використано код. Секрети або облікові дані Хорошопа в записах не зберігаються.

## Банер із промокодом

Тип кампанії має значення `promo_code`. У конструкторі код вибирається через модальне вікно бібліотеки з пошуком і фільтром статусу. Новий запис можна створити прямо з цього вікна. Кампанію не можна зберегти без вибраного `promoCodeId`.

Банер показує:

- необов'язкові надзаголовок, заголовок і основний текст кампанії;
- величину пропозиції;
- код і кнопку копіювання;
- необов'язковий CTA, якщо задано URL.

`Exit intent` є умовою появи, а не окремим типом банера, тому він доступний і для банера з промокодом. Обмеження для товарного промобанера й автоматичної альтернативи відсутнього товару залишаються окремими.

## Незмінний snapshot публікації

Кампанія зберігає два різні знімки:

1. Чернетковий snapshot оновлюється під час збереження кампанії з поточного запису бібліотеки.
2. Опублікований snapshot створюється під час публікації й використовується публічним runtime.

Редагування, завершення або вимкнення коду в бібліотеці не змінює вже опублікований банер. Щоб банер отримав нові дані, кампанію треба зберегти та повторно опублікувати. Це виключає непомітну зміну активної реклами.

## Поведінка на вітрині

Кнопка **«Копіювати»** використовує Clipboard API з безпечним fallback для старих браузерів. KramKit не шукає поле промокоду в DOM Хорошопа і не вводить значення автоматично. Така межа однакова для desktop і mobile та не залежить від різних селекторів цих поверхонь.

CTA веде лише на явно заданий у кампанії URL. Публічний runtime використовує тільки опублікований snapshot, а не актуальний запис бібліотеки.

## Аналітика

Для банерів із промокодом фіксуються:

- `impression` — показ;
- `copy` — успішне копіювання коду;
- `promo_cta` — перехід за CTA;
- `dismiss` — закриття;
- `click` та `acknowledge` — спільні події платформи, якщо відповідна дія присутня.

В аналітиці показуються кількість копіювань, переходи за CTA і конверсія копіювання: `copy / impression × 100%`. Подія `copy` надсилається лише після успішного копіювання через основний механізм або fallback.

## Перевірки сумісності

Інтеграційні тести мають підтверджувати:

- ізоляцію бібліотек за магазином і case-insensitive унікальність коду;
- незмінність опублікованого snapshot після редагування бібліотеки;
- оновлення snapshot лише після повторної публікації;
- рендер банера, копіювання та CTA;
- відсутність автоматичного застосування коду;
- однакову функціональність runtime з desktop і mobile User-Agent та viewport.
